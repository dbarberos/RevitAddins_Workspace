## 2. The Revit API "Wall" (Execution Context)

The biggest obstacle to implementing Unit Testing in Revit is that the `RevitAPI.dll` library is tightly coupled to the `Revit.exe` executable (the Host). 
If you create a standard test project (`dotnet test`) and try to instantiate a native object, such as `XYZ dot = new XYZ(0,0,0)`, the test will immediately fail with a native C++ exception, because the Revit memory context is not initialized.

To solve this, the architecture is divided into two fundamental strategies: **Out-of-Process Testing (Mocking)** and **In-Process Testing**.

---

## 3. Out-of-Process Testing and Wrapper Pattern (Mocking)

To test *business logic* (math, string validations, clustering algorithms) instantly without opening Revit, you must completely separate the Revit code from the business code.

Because Autodesk classes (e.g. `Wall`, `Document`) are often 'sealed' or have private constructors, they cannot be easily 'Mocked' with libraries like `Moq`. The solution is the **Wrapper/Adapter Pattern**.

## 4. In-Process Testing (Revit Test Frameworks)

There is code that *must* needs the Revit database (e.g. testing if a complex `FilteredElementCollector` works, or if a Wall is created correctly).

For this, specialized Frameworks are used (such as Speckle's **xUnitRevit** or Dynamo's **RevitTestFramework**) that start Revit in Headless mode, load an empty test model (`.rvt`), run the `xUnit` tests using the real API, and close the process.

## 5. Agent Injection Instructions (Prompting Prompt)

*When you are required to design code that must be rigorously tested, or write unit tests, strictly apply these architectural guidelines:*

1. **Domain Isolation (Clean Architecture):** It is strictly prohibited to use native classes from the `Autodesk.Revit.DB` namespace within service classes that contain mathematical, business or algorithmic validation logic. The agent MUST force the creation of DTOs (Data Transfer Objects) or Wrapper interfaces to transfer information from Revit to the domain layer.
2. **Principle of Single Responsibility in Commands:** The `Execute` method inherited from `IExternalCommand` MUST be completely empty of logical conditionals (`if/else/for`) referring to the business. Your only responsibility should be to collect the context (`ExternalCommandData`), instantiate the Wrappers, inject them into the core business class, and manage the transaction and the return of the `Result`.
3. **Rollback in Integration Tests:** If you schedule an In-Process test that modifies the Revit model (creation, editing or deletion of elements), you MUST end the `Transaction` block by invoking `.RollBack()` instead of `.Commit()`. This guarantees the idempotence of the tests (the model remains identical so that the next test does not fail due to "garbage" generated by the previous test).
4. **Don't Mock Revit Classes:** Never try to mock native Autodesk classes (e.g. `var mockWall = new Mock<Wall>()`) as it will throw Castle.DynamicProxy exceptions due to lack of public constructors or inheritance modifiers. Always simulate proprietary interfaces of your own design.
