# ⚠️ CRITICAL RULES: Thread Context and Revit API Safety

> These rules are the result of intensive debugging. Ignoring them produces silent crashes and unexpected Revit closures without any error message.

## 🚫 FORBIDDEN: Calling the Revit API from the WPF Thread

**NEVER** call any Revit API (`FilteredElementCollector`, `Document`, `UIDocument`, `Selection`, etc.) from:
- A `Dispatcher.BeginInvoke()` or `Dispatcher.Invoke()`
- A `Task.Run()` or background thread
- A WPF event handler (button click, RadioButton change, `PropertyChanged`, etc.)
- A `partial void OnXxxChanged()` generated by CommunityToolkit MVVM if it is bound to a WPF control

**Any call to the Revit API outside the correct context CLOSES Revit with no error message.**

### SAFE Contexts for calling the Revit API:

| Context | Safe |
|---|---|
| `IExternalCommand.Execute()` | ✅ |
| `IExternalEventHandler.Execute(UIApplication app)` | ✅ |
| `IExternalApplication.OnStartup()` | ✅ |
| `Application.Idling` event (registered handler) | ✅ |
| `Dispatcher.BeginInvoke` / `Task.Run` | ❌ CRASH |
| `partial void OnXxxChanged()` (CommunityToolkit) | ❌ CRASH |
| Background thread / `async void` | ❌ CRASH |

---

## ✅ RECOMMENDED PATTERN: Pre-fetch in the ViewModel constructor

When a ViewModel needs Revit data that may change based on user interaction (e.g. scope change), **pre-load all possible data in the ViewModel constructor**, which is called from `IExternalCommand.Execute()` (safe context).

```csharp
// ✅ CORRECT: Constructor called from Execute() – safe API context
public SelectionFilterViewModel(RevitSelectionService service)
{
    // All scopes are pre-loaded here, in the correct API context
    _currentSelectionElements = service.GetAvailableElements(SelectionScope.CurrentSelection);
    _elementsInViewElements   = service.GetAvailableElements(SelectionScope.ElementsInView);
    _allModelElements         = service.GetAvailableElements(SelectionScope.AllModelElements);
}

// ✅ CORRECT: scope change only swaps memory pointers – no API calls
partial void OnCurrentScopeChanged(SelectionScope value)
{
    _activeElements = value switch {
        SelectionScope.ElementsInView   => _elementsInViewElements,
        SelectionScope.AllModelElements => _allModelElements,
        _                               => _currentSelectionElements
    };
    BuildTreeFromMemory(); // Only operates on data already loaded in memory
}
```

```csharp
// ❌ INCORRECT: Revit API call from WPF thread – Guaranteed CRASH
partial void OnCurrentScopeChanged(SelectionScope value)
{
    Dispatcher.BeginInvoke(() => {
        var elements = new FilteredElementCollector(_doc, _doc.ActiveView.Id); // 💥 CLOSES REVIT
    });
}
```

## ✅ ALTERNATIVE PATTERN: IExternalEventHandler (for on-demand data)

Use this when the data is too large to pre-load or needs real-time updating. It is more complex but correct.

```csharp
// 1. Handler: executes on the Revit API thread
public class FetchElementsHandler : IExternalEventHandler
{
    public void Execute(UIApplication app)
    {
        // ✅ SAFE: we are in the Revit API context
        var elements = new FilteredElementCollector(app.ActiveUIDocument.Document)
            .WhereElementIsNotElementType().ToList();
        _viewModel.UpdateData(elements); // return data to the ViewModel via callback
    }
    public string GetName() => "FetchElements";
}

// 2. Startup: create the ExternalEvent INSIDE the Command's Execute()
var handler = new FetchElementsHandler(viewModel);
var externalEvent = Autodesk.Revit.UI.ExternalEvent.Create(handler); // ✅

// 3. From WPF: just .Raise() – never direct Revit data
partial void OnCurrentScopeChanged(SelectionScope value)
{
    handler.SetScope(value);
    externalEvent.Raise(); // ✅ safe from any thread – just signals Revit
}

// 4. The ViewModel receives the data already in the correct context and sends it to the UI
public void UpdateData(List<ElementModel> elements)
{
    // Now we can go to the Dispatcher to update the UI
    _uiDispatcher.BeginInvoke(() => BuildTree(elements));
}
```

### ⚠️ Warning about `ExternalEvent` with `Nice3point.Revit.Toolkit`
- `Nice3point.Revit.Toolkit.External.ExternalEvent` and `Autodesk.Revit.UI.ExternalEvent` are **distinct types with the same name**.
- Always use the fully qualified name `Autodesk.Revit.UI.ExternalEvent.Create(handler)` to avoid compilation ambiguity errors (CS0104).

## ❌ ANTI-PATTERN: DoEvents / PushFrame on the Revit UI thread

**NEVER** implement a `DoEvents()` (based on `DispatcherFrame`) inside callbacks that execute during heavy Revit loading operations. This causes:
- Re-entry into the Windows message loop
- Indefinite blocking of the UI thread
- Forced closure of Revit

```csharp
// ❌ FORBIDDEN inside Revit Add-ins – causes deadlock and Revit closure
private static void DoEvents()
{
    var frame = new System.Windows.Threading.DispatcherFrame();
    Dispatcher.CurrentDispatcher.BeginInvoke(DispatcherPriority.Background, ExitFrame, frame);
    Dispatcher.PushFrame(frame); // 💥 deadlock in Revit context
}
```

## ✅ Safe cross-thread logging in Revit Add-ins

For a logging service that works from any thread (API or WPF), capture the `Dispatcher` at startup and **always use `BeginInvoke` (not `Invoke`)** for log messages. Never use `DoEvents` to force a refresh.

```csharp
public static class LoggerService
{
    private static Dispatcher _uiDispatcher;
    
    // Call from StartupCommand.Execute() – safe context
    public static void SetDispatcher(Dispatcher d) => _uiDispatcher = d;

    public static void LogInfo(string message)
    {
        string entry = $"[{DateTime.Now:HH:mm:ss.fff}] {message}";
        System.Diagnostics.Debug.WriteLine(entry); // always visible in VS Output
        
        // BeginInvoke (asynchronous): never blocks the calling thread
        _uiDispatcher?.BeginInvoke(new Action(() => Logs.Insert(0, entry)));
        // ❌ Never use Invoke() or PushFrame() to "force" the refresh
    }
}
```
